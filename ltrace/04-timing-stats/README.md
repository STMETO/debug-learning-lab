# 实验 04：时间与统计 —— 谁是最慢的库函数？

> 🎯 **目标**：用 `-t`/`-T` 给每个调用加上时间戳和耗时，用 `-c` 生成统计摘要。
>
> ⏱️ 约 15 分钟
>
> 📖 **前置**：[实验 03](../03-filtering/)（过滤）

---

## 先看示例程序

[slow.c](slow.c) 有四种不同耗时特征的场景：

| 阶段 | 操作 | 预期 |
|------|------|------|
| A | `strlen` × 10 + `isdigit` × 10 | 微秒级，极快 |
| B | `strdup` + `free` × 5 | 毫秒级 |
| C | `sleep(1)` × 3 | 秒级——明显的瓶颈 |
| D | 循环中反复调 `strlen` | 调用次数异常高 |

```bash
make && ./slow
```

> 提示：运行需要 ~3 秒（3 次 sleep）。

---

## 实验开始

### 第一步：`-t -T` —— 时间戳 + 耗时

```bash
ltrace -t -T -e strdup+free+sleep+strlen ./slow
```

输出（关键行）：

```
08:50:09 slow->strdup("this is a medium-length...") = 0x... <0.000381>
08:50:09 slow->free(0x...)                         = <void> <0.000512>
08:50:09 slow->strdup("this is a medium-length...") = 0x... <0.000498>
...
08:50:09 slow->sleep(1)                            = 0 <1.002074>
08:50:10 slow->sleep(1)                            = 0 <1.001020>
08:50:11 slow->sleep(1)                            = 0 <1.001842>
08:50:12 slow->strlen("frequency analysis...")     = 30 <0.001322>
```

解读：

| 调用 | 开始时间 | 耗时 | 数量级 |
|------|---------|------|--------|
| `strdup` | `08:50:09` | `<0.000381>` = 381 微秒 | 微小 |
| `sleep(1)` | `08:50:09` | `<1.002074>` = 1,002,074 微秒 | **巨大** |
| `strlen` | `08:50:12` | `<0.001322>` = 1322 微秒 | 较大 |

> `sleep` 比 `strdup` 慢 ~2600 倍。`-T` 让你一眼看出谁在拖慢程序。

### 第二步：从时间戳看调用间隔

```
08:50:09 slow->sleep(1) = 0 <1.002>    ← sleep #1 结束（耗时 1.002s，时间来到 10.002s）
08:50:10 slow->sleep(1) = 0 <1.001>    ← sleep #2 开始（时间戳 08:50:10 → 是 10.002s 的秒级显示）
```

`-t` 和 `-tt` 的格式同 strace：

| 选项 | 格式 | 精度 |
|------|------|------|
| `-t` | `HH:MM:SS` | 秒 |
| `-tt` | `HH:MM:SS.μs` | 微秒 |
| `-ttt` | Unix 时间戳 | 微秒（适合脚本） |

### 第三步：`-c` —— 一张统计表看清全局

```bash
ltrace -c ./slow
```

输出：

```
% time     seconds  usecs/call     calls      function
------ ----------- ----------- --------- --------------------
 99.26    3.006821     1002273         3 sleep
  0.33    0.009854         317        31 strlen
  0.12    0.003735         373        10 __ctype_b_loc
  0.12    0.003707         411         9 puts
  0.06    0.001820         303         6 strdup
  0.06    0.001738         434         4 printf
  0.05    0.001660         276         6 free
------ ----------- ----------- --------- --------------------
100.00    3.029335                    69 total
```

### 从这张表能挖出什么？

**1. 时间杀手**：

```
sleep: 99.26% of time, 3 calls, 1,002,273 μs/call
→ sleep 占了几乎全部时间——想加速程序？先去掉 sleep
```

**2. 调用频率异常**：

```
strlen: 31 calls
→ 程序里只有几个明显的 strlen，为什么调了 31 次？
→ 看阶段 D 的代码:
   for (int i = 0; text[i]; i++) {
       total += strlen(text + i);  // 每次迭代都调 strlen！
   }
→ 这是一个 O(n²) 的意外！31 次 strlen 在一个 30 字符的字符串上
```

> **ltrace `-c` 帮你发现隐藏的性能陷阱**：调用次数远超出你预期的函数，需要重新审视代码逻辑。

**3. 调用频率正常**：

```
malloc: 0 次（没有直接出现在统计中——被 strdup 内部调用了？）
strdup: 6 calls（阶段 B 的 5 次 + 阶段 D 的 1 次 ✓）
free: 6 calls（配对 ✓）
```

**4. 内部函数暴露**：

```
__ctype_b_loc: 10 calls, 373 μs/call
→ 这是 isdigit/ctype 的内部实现函数——你写了 isdigit，实际调的是它
```

### 第四步：`-c` + `-e` —— 只看感兴趣的函数

```bash
ltrace -c -e strlen+strdup+free+memcpy ./slow
```

只统计指定的函数——排除 sleep 等已知瓶颈，聚焦你关心的部分。

---

## 📝 命令小结

| 选项 | 作用 |
|------|------|
| `-t` | 每行前加时间戳（精确到秒） |
| `-tt` | 每行前加时间戳（精确到微秒） |
| `-T` | 每行末尾加耗时 |
| `-c` | 程序结束时打印统计摘要 |
| `-c -e 函数1+函数2` | 只统计指定函数的摘要 |

## 🧪 试试看

1. 用 `ltrace -c ./slow`，找出调用次数最多的函数——是你预期的吗？
2. 把阶段 D 的 `strlen` 循环改为先存下 `strlen(text)` 再循环，`-c` 中 `strlen` 的调用次数从 31 变成多少？
3. 用 `ltrace -tt -T -e sleep ./slow`——`sleep(1)` 的精确耗时是正好 1 秒吗？偏差多大？
4. `-c` 报告中 `__ctype_b_loc` 是什么？为什么它出现在你的程序的统计里？

## 常见错误

| 现象 | 原因 | 解决 |
|------|------|------|
| `-c` 耗时总和远大于实际运行时间 | ltrace 自身的追踪开销也被计入 | 正常——`-c` 中的时间是带追踪开销的 |
| `-c` 中 `% time` 加起来不到 100% | 可能有你没追踪的函数在消耗时间 | 先用全量 `-c`，再加 `-e` 过滤 |
| `-T` 和 `-c` 同时用时输出混乱 | `-c` 的汇总会覆盖 `-T` | 分开用——先用 `-c` 找瓶颈，再用 `-T` 细看 |
