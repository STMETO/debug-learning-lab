# 实验 06：统计模式 —— 不用逐行读日志，一张表看清全局

> 🎯 **目标**：用 `strace -c` 生成系统调用的统计摘要——次数、耗时、错误率，一张表看清程序的"系统调用画像"。
>
> ⏱️ 约 10 分钟
>
> 📖 **前置**：[实验 03](../03-filtering/)、[实验 04](../04-timing/)

## 什么时候用 `-c`？

当你不想逐行读几十上百条 strace 输出，而是想要一个"全局概览"：

```
程序一共发起了多少次 write？  → strace -c 告诉你
哪个调用花了最多时间？        → strace -c 告诉你
有多少次系统调用失败了？      → strace -c 告诉你
```

---

## 先看示例程序

[many.c](many.c) 混合了各种操作：

- 20 次 `write`（文件写入）
- 3 次 `read`（文件读取）
- 10 次 `malloc/free` 循环
- 5 次 `usleep`
- 1 次大内存分配

```bash
make && ./many
```

## 实验开始

### 运行统计模式

```bash
strace -c ./many
```

输出：

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 30.65    0.001036          49        21           write
 18.17    0.000614         307         2           munmap
 11.12    0.000376          94         4           openat
 10.09    0.000341          68         5           clock_nanosleep
  7.87    0.000266          66         4           mprotect
  3.85    0.000130          32         4           close
  3.67    0.000124          31         4           read
  3.05    0.000103          34         3           brk
  2.99    0.000101          33         3           lseek
  1.57    0.000053          17         3           newfstatat
  1.27    0.000043           4         9           mmap
  ...                                              ...
------ ----------- ----------- --------- --------- ----------------
100.00    0.003380          43        77         2 total
```

---

### 逐列解读

| 列 | 含义 | 问题 |
|----|------|------|
| `% time` | 该调用占总耗时的百分比 | "时间花在哪了？" |
| `seconds` | 该调用的总耗时 | "精确花了多少秒？" |
| `usecs/call` | 每次调用的平均耗时（微秒） | "单次调用快不快？" |
| `calls` | 调用次数 | "这个调用被触发了几次？" |
| `errors` | 失败的次数 | "有多少次调用返回了 -1？" |
| `syscall` | 系统调用名称 | — |

### 从这张表能看出什么？

**1. 时间花在哪里？**

```
% time 最高的 3 个：
  write      30.65%
  munmap     18.17%
  openat     11.12%
```

20 次 `write` 占了总耗时的 30%，每笔平均 49 微秒——正常。

**2. 哪些调用被用得最多？**

```
calls 最高的 3 个：
  write      21 次   ← 我们写的 20 行 + 1 次 stdout
  mmap        9 次   ← glibc 的内存映射（启动开销）
  clock_nanosleep  5 次   ← 5 次 usleep
```

**3. 有没有失败的调用？**

```
errors 列：
  2  total    ← 总共 2 次失败
  access  → 1 error（/etc/ld.so.preload 不存在）
  arch_prctl → 1 error
```

> 关注 `errors` 列：如果某个调用的错误比例很高，它在 strace 逐行输出中就是那些 `= -1 ERRNO` 的行。

**4. 平均耗时正常吗？**

```
usecs/call 最高的：
  munmap    307 μs  ← 释放内存映射（正常范围）
  openat     94 μs  ← 打开文件（正常范围）
  clock_nanosleep 68 μs  ← sleep 调用本身的开销

如果某个调用的 usecs/call 异常高：
  → 可能磁盘慢、网络慢、或内核资源争用
```

### `-c` 也可以和 `-e` 组合

```bash
# 只看文件类调用的统计
strace -c -e trace=file ./many

# 只看特定几个调用
strace -c -e trace=openat,read,write ./many
```

### `-C` 实时模式

`-c` 只在程序结束时打印汇总表。`-C` 是实时模式：

```bash
strace -C ./many
```

程序运行过程中，`Ctrl-C` 时打印**到目前为止**的汇总——适合分析长时间运行的程序。

### `-w` 只统计耗时

```bash
strace -c -w ./many
```

`-w` 按"每次调用的总耗时"而不是"syscall 时间"排序——`clock_nanosleep` 这种等待型的调用会排到最前面。

## 📝 统计模式诊断清单

```
1. 看 % time 最高的是哪几个 → 优化重点
2. 看 errors 列 → 哪些调用在失败
3. 看 usecs/call 异常高的 → 可能的内核瓶颈
4. 看 calls 特别多的 → 是否有不必要的重复调用
```

### 常见模式速查

| 现象 | 可能的问题 |
|------|-----------|
| `write` 次数很多但每次只写几字节 | 没开缓冲（`setbuf`） |
| `openat` + `close` 同一文件反复出现 | 文件没缓存，每次循环重新打开 |
| `clock_nanosleep` 时间很长 | 程序在等什么（网络/定时器） |
| `read` 返回很小但 calls 很多 | 读缓冲太小 |

## 🧪 试试看

1. 用 `strace -c ls /tmp` 和 `strace -c ls /` —— 两个目录的 `ls` 产生的调用次数有什么不同？
2. 用 `strace -c -e trace=file ./many` —— 只看文件操作的统计
3. 写一个无限循环的程序，用 `strace -C` 追踪它，`Ctrl-C` 后看实时汇总
4. `errors` 列中 `access` 调用为什么会有 1 次错误？（提示：`/etc/ld.so.preload`）

## 常见错误

| 现象 | 原因 | 解决 |
|------|------|------|
| `-c` 输出中某些调用看不到 | 可能被过滤了 | `-c` 可以单独用，也可以和 `-e` 组合 |
| `seconds` 总和很小（毫秒级） | 程序本身很快 | 正常——`-c` 更适合分析运行 1 秒以上的程序 |
| `% time` 加起来不到 100% | strace 自身开销没计入 | 正常 |
