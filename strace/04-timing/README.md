# 实验 04：时间分析 —— 找出"慢"的源头

> 🎯 **目标**：用 `-t`/`-tt`/`-T` 给每个系统调用打上时间戳和耗时，精确定位性能瓶颈。
>
> ⏱️ 约 15 分钟
>
> 📖 **前置**：[实验 03](../03-filtering/)（过滤）+ [实验 02](../02-read-output/)（读懂 `<耗时>`）

## 三个时间选项，三个层次

```
-t    粗略时间    "14:32:05"           —— 只精确到秒
-tt   精确时间    "14:32:05.323292"    —— 精确到微秒
-T    耗时        "<0.000219>"          —— 这个调用花了多久
```

组合 `-tt -T` = 每行前面是"什么时候发生的"，末尾是"花了多久"。

---

## 先看示例程序

[slow.c](slow.c) 有四个阶段，耗时各不相同：

| 阶段 | 操作 | 预期耗时 |
|------|------|---------|
| A 快速 | `getpid()` 两次 | 微秒级 |
| B 中等 | 文件读写 10 行 + 读取 | 毫秒级 |
| C 慢速 | `usleep(200000)` × 3 | 秒级 |
| D 大内存 | `malloc + memset` 10MB | 十到百毫秒级 |

```bash
make && ./slow
```

## 实验开始

### 第一步：`-tt -T` 组合 —— 最完整的时序视图

```bash
strace -tt -T -e trace=openat,write,read,close,clock_nanosleep ./slow
```

截取输出中关键的四段：

**阶段 B（文件写入）**——毫秒级：

```
08:16:56.333607 openat(..., "/tmp/strace_timing.txt", ...) = 3 <0.000411>
08:16:56.334286 write(3, "Line 0: this is a timing...", 36) = 36 <0.000124>
08:16:56.334606 write(3, "Line 1: this is a timing...", 36) = 36 <0.000100>
08:16:56.334890 write(3, "Line 2: this is a timing...", 36) = 36 <0.000100>
...
08:16:56.337610 write(3, "Line 9: this is a timing...", 36) = 36 <0.000125>
08:16:56.338030 close(3)                = 0 <0.000170>
08:16:56.338446 openat(..., "/tmp/strace_timing.txt", O_RDONLY) = 3 <0.000157>
08:16:56.338874 read(3, "Line 0: ...", 2048)  = 360 <0.000156>
08:16:56.339303 close(3)                = 0 <0.000112>
```

> 10 次 write 总共花了约 **5 毫秒**（从 `08:16:56.333` 到 `08:16:56.338`）。每个单独的 write 耗时 ~100 微秒。

**阶段 C（sleep）**——秒级：

```
08:16:56.339626 clock_nanosleep(..., {tv_sec=0, tv_nsec=200000000}, ...) = 0 <0.201226>
08:16:56.541150 clock_nanosleep(..., {tv_sec=0, tv_nsec=200000000}, ...) = 0 <0.200978>
08:16:56.742591 clock_nanosleep(..., {tv_sec=0, tv_nsec=200000000}, ...) = 0 <0.200682>
```

> 三次 sleep 各 ~0.2 秒，时间戳依次递增 0.2 秒。`<耗时>` 约 0.2 = 200ms = 200000 微秒。

**所有输出去掉后**，最终程序 stdout 的那行：

```
08:16:56.966175 write(1, "=== strace ...", ...) = 306 <0.000235>
```

### 第二步：解读时间戳 —— 找出"间隙"

时间戳不仅告诉你每个调用花了多久，还能揭示**调用之间的间隙**：

```
08:16:56.339626 clock_nanosleep(...) = 0 <0.201226>    ← sleep #1 结束
08:16:56.541150 clock_nanosleep(...) = 0 <0.200978>    ← sleep #2 开始
```

`08:16:56.541150 - 08:16:56.339626 = 0.201524 秒`。这 0.2 秒的间隙 = 用户态代码（`printf`、循环逻辑）的执行时间 + strace 自身开销。

> 用时间戳算间隙：`下一个调用的开始 - 上一个调用的结束 = 用户态代码耗时`。strace 不能直接看到用户态代码，但时间差暴露了它。

### 第三步：对比耗时 —— 谁是瓶颈？

把四种操作的耗时排序：

| 系统调用 | 耗时 | 数量级 |
|---------|------|--------|
| `write` (stdout) | `<0.000235>` | ~200 微秒 |
| `openat` | `<0.000411>` | ~400 微秒 |
| `read` (360 bytes) | `<0.000156>` | ~150 微秒 |
| `clock_nanosleep` | `<0.201000>` | **200,000 微秒** |

> `clock_nanosleep` 比其它调用慢**1000 倍以上**。如果你的程序"感觉慢"，strace `-T` 会告诉你时间花在了哪种调用上。

### 第四步：`-t` vs `-tt` —— 什么时候用哪个

```bash
# -t: 只有时分秒（适合看"大概什么时候发生了什么"）
strace -t ./slow
# 输出: 14:32:05 openat(...)

# -tt: 带微秒（适合精确计算时间差）
strace -tt ./slow
# 输出: 14:32:05.323292 openat(...)

# -ttt: Unix 时间戳（适合导入脚本/数据库分析）
strace -ttt ./slow
# 输出: 1719891125.323292 openat(...)
```

| 选项 | 格式 | 适合场景 |
|------|------|---------|
| `-t` | `HH:MM:SS` | 快速浏览 |
| `-tt` | `HH:MM:SS.μs` | 精确分析 |
| `-ttt` | Unix 时间戳 | 脚本处理 |

## 📝 时间分析三件套

```
strace -tt -T -e trace=file ./program

  -tt    每一行前面加微秒级时间戳
  -T     每一行末尾加耗时
  -e     只看文件操作（减少噪音）

输出示例：
14:32:05.323292 openat(..., "data.txt", ...) = 3 <0.000411>
 │            │                                      │
 │            │                                      └─ 花了 411 微秒
 │            └─ 发生时间精确到微秒
 └─ 可计算两个调用间的用户态耗时
```

## 🧪 试试看

1. 用 `strace -tt -T ./slow`（不加 `-e`），找到耗时最长的 3 个调用——是哪 3 个？
2. 计算阶段 B 中 10 次 `write` 的总耗时——总和超过 1 毫秒了吗？
3. `-ttt` 格式的时间戳和 `-tt` 有什么换算关系？（提示：Unix 纪元的起点）
4. 写一个程序调用 `sleep(2)`，用 strace 验证——实际耗时是正好 2 秒还是略有偏差？

## 常见错误

| 现象 | 原因 | 解决 |
|------|------|------|
| 耗时 `<0.000001>` 看起来不真实 | 系统调用本身比计时精度还快 | 正常——极快的调用计时精度有限 |
| 加了 `-T` 后时间戳不准了 | `-T` 的计时有轻微开销 | 影响极小（<1%），可以忽略 |
| 某个调用耗时 0 但实际等了很久 | 进程可能在另一个调用里阻塞了 | 看上一个耗时长且卡住的调用 |
