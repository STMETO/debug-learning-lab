# 实验 08：Core Dump 分析 —— 程序崩溃了，怎么事后破案？

> 🎯 **目标**：学会生成和分析 core dump 文件，在程序崩溃后进行事后调试。
>
> ⏱️ 约 15 分钟
>
> 📖 **前置**：[实验 05](../05-backtrace/)（你需要会看 `backtrace` 和切换 `frame`）

## 这是什么场景？

```
凌晨 3:00，服务器上的程序崩溃了。
你没有 GDB 连着它，你没有看到现场，你只有一具"尸体"。
你怎么知道它死在哪里、怎么死的？
```

**Core dump**（核心转储）就是程序的"案发现场快照"——崩溃那一刻，操作系统把程序的内存、寄存器、调用栈全部写入一个文件，供你事后分析。

---

## 先看示例程序

[crash.c](crash.c) 是一个故意埋了 bug 的程序：

```
mode 0: description 是 NULL → strlen(NULL) → 段错误 💥
mode 1: 正常执行
mode 2: 内存分配可能失败
```

```bash
make

# 正常模式
./crash 1

# 崩溃模式（留到后面再用）
# ./crash 0
```

---

## 准备：让系统生成 core dump

在让程序崩溃之前，你需要告诉操作系统："我要 core dump"。

```bash
# 1. 允许生成任意大小的 core 文件
ulimit -c unlimited

# 2. 确认设置生效
ulimit -c
# 输出: unlimited

# 3. （Linux 上可能还需要）设置 core 文件的生成路径
# 有些系统默认把 core dump 发给 systemd-coredump 或 apport
# 如果下面的实验中看不到 core 文件，试试：
echo "core.%p" | sudo tee /proc/sys/kernel/core_pattern
```

> ⚠️ **Docker/WSL 用户**：如果你的环境无法修改 `kernel.core_pattern`（只读文件系统），
> 跳过上面第 3 步，使用后面的"方法二：gcore"——效果完全一样。

## 实验开始

### 方法一：传统的 core dump 分析

```bash
# 让程序崩溃（不要在 GDB 里跑！直接在终端跑）
./crash 0
```

输出：

```
=== Core Dump 实验 ===
运行模式: 0

配置信息:
名称: test
数值: 42
Segmentation fault (core dumped)    ← 出现这行！
```

当前目录下会多出一个 `core` 或 `core.<pid>` 文件：

```bash
ls -l core*
```

现在用 GDB 加载 core dump：

```bash
gdb ./crash core
```

GDB 的输出会告诉你：

```
Core was generated by './crash 0'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  description_length (desc=0x0) at crash.c:16
16      return strlen(desc);
```

关键信息：
- **SIGSEGV**：崩溃信号是段错误（非法内存访问）
- **#0 description_length (desc=0x0)**：崩溃点——`desc` 是 `NULL` 指针（`0x0`）
- **crash.c:16**：崩溃发生在第 16 行

### 分析崩溃现场

```bash
(gdb) backtrace
```

输出：

```
#0  description_length (desc=0x0) at crash.c:16
#1  0x... in print_config (cfg=0x7ffc...) at crash.c:23
#2  0x... in main (argc=1, argv=0x7ffc...) at crash.c:62
```

调用链一目了然：`main → print_config → description_length`。第 `#0` 层传入了 `NULL`。

```bash
(gdb) frame 0
(gdb) print desc
$1 = 0x0                    ← NULL！这就是崩溃原因
```

从第 `#1` 层看是谁传的 NULL：

```bash
(gdb) frame 1
(gdb) info locals
```

```
cfg = 0x7ffc...
len = 24592                 ← 未初始化的垃圾值（证明这行还没执行）
```

```bash
(gdb) print cfg->description
$2 = 0x0                    ← 结构体的 description 字段是 NULL
```

现在跳到 `main`（第 `#2` 层）：

```bash
(gdb) frame 2
(gdb) info locals
```

```
cfg = {name = "test", value = 42, description = 0x0}
```

> **破案了**：`main` 里的 `cfg.description` 是 `NULL`，被一路传到了 `description_length` → `strlen(NULL)` → 段错误。回到源码找到 `setup_broken_config`，mode=0 时确实把 `description` 设成了 `NULL`。

### 方法二：用 gcore（不依赖系统 core 配置）

如果你的环境不能生成 core 文件，GDB 提供了 `gcore` 命令——在程序崩溃**之前**手动生成 core dump：

```bash
gdb ./crash
```

```bash
(gdb) break description_length
(gdb) run
```

程序停在崩溃前一瞬间：

```
Breakpoint 1, description_length (desc=0x0) at crash.c:16
```

```bash
(gdb) gcore /tmp/crash.core
# 输出: Saved corefile /tmp/crash.core
```

现在你可以在**另一个终端**或以后分析这个 core 文件：

```bash
gdb ./crash /tmp/crash.core
```

## Core dump 里有什么？

| 信息 | 对应命令 |
|------|---------|
| 崩溃信号（SIGSEGV / SIGABRT / ...） | 加载时自动显示 |
| 崩溃时的调用栈 | `backtrace` |
| 每一层的参数和局部变量 | `frame N` → `info locals` / `info args` |
| 所有线程的栈（多线程程序） | `thread apply all backtrace` |
| 全局变量的值 | `print 变量名` |
| 寄存器的值 | `info registers` |

> 除了不能 `next` / `step` / `continue`（程序已经死了），core dump 几乎保留了调试所需的全部信息。

---

## 📝 命令小结

| 命令 | 作用 |
|------|------|
| `ulimit -c unlimited` | 允许生成任意大小的 core 文件 |
| `gdb ./程序 core文件` | 加载 core dump 进行分析 |
| `gcore 文件路径` | 在 GDB 内手动生成 core dump（无需系统配置） |
| `backtrace` / `bt` | 查看崩溃时的调用栈 |
| `frame N` | 跳转到第 N 层栈帧 |
| `info registers` | 查看 CPU 寄存器（崩溃瞬间的值） |

## 🧪 试试看

1. 用 mode=0 运行崩溃后，分析 core dump，崩溃时 CPU 的 `rip` 寄存器指向哪个地址？（`info registers rip`）
2. mode=2 会崩溃吗？先猜，再试，再用 core dump 分析
3. 在 `print_config` 的 `description_length` 调用前加一个 `if (cfg->description == NULL)` 检查，能修好这个 bug 吗？试着改代码验证
4. 对比：用 GDB 直接 `run`（活体调试）和用 core dump 分析（尸体解剖），各有什么优势？

## 常见错误

| 现象 | 原因 | 解决 |
|------|------|------|
| 没有生成 core 文件 | `ulimit -c` 是 0（禁止生成） | `ulimit -c unlimited` |
| core 文件在奇怪的位置 | `kernel.core_pattern` 配置了管道 | 用 `gcore` 替代，或修改 `/proc/sys/kernel/core_pattern` |
| 加载 core 后 `bt` 全是 `??` | core 文件和可执行文件不匹配 | 确保用编译时**同一个**可执行文件分析 |
| `print` 报 `No symbol "x"` | 编译时没加 `-g` | 重新 `make`（确保 `-g` 在 CFLAGS 里） |
